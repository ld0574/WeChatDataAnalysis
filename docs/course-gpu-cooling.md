# 课程任务的降功耗续跑

用户因房间升温暂停后，于 2026-11-02 明确要求继续。本次将 RTX 2080 Ti 的 GPU 0 功耗上限从 280W 调至 120W，先只恢复课程主任务，保留原有 ASR、摘要和画面断点。PDF、动画及其他 GPU 批处理暂不同时启动。降低功耗可能增加处理时间，也不代表房间温度不会继续变化。

同日用户进一步说明夜间可以提高功耗，本次夜间上限改为 200W，温度暂停阈值仍为 70°C。通过 `--maximum-power 200` 显式设置守护上限，硬件功耗上限也须先设置为不高于该值。变更前先暂停旧守护和工作进程，确认退出后再从断点恢复，避免同时启动两个主任务。

新增 `course_gpu_guard` 独立运行，不修改生产提取模块或既有监督程序的指纹。启动前核对实际温度与功耗上限，要求显式 `--resume` 才移开已存在的暂停标记，并保留旧标记。默认每 5 秒检查一次：温度达到 70°C、硬件功耗上限超过 120W、传感器读取失败或用户创建暂停标记时，写入全局暂停与监督停止标记，卸载本次使用的 Qwen 模型，并等待当前任务退出。

上述 120W 是默认守护参数；夜间显式配置后，以状态文件中的 `maximum_power_limit_w=200` 为准。硬件功耗上限约束的是驱动功耗控制，瞬时采样可能高于设定值，不能把它描述为每个采样点的绝对功耗保证。

任务未在等待窗口退出时，仅结束本守护启动的进程树；已提交断点保留，未提交批次下次重试。守护不自动恢复，也不重启失败的工作进程。正常完成后记录实际退出码，不将退出等同于全量归档或语义验收。

本机 `output/course-knowledge/gpu-thermal-guard.json` 记录进程、时间、温度、功耗上限和真实阶段。原始 `supervisor-stop.flag` 在单任务续跑时保持存在，避免旧监督任务意外恢复全部 GPU 队列。用户再次暂停后，恢复仍需明确操作；系统 Goal 卡片的恢复是单独的应用状态，不能以本地进程已运行冒充卡片已恢复。

本次硬件功耗上限不是项目级设置，会影响同一显卡上的其他程序，重启或驱动更新后也可能恢复默认。监控发现功耗上限改变会暂停任务。后续恢复默认功耗须结合用户意愿和发热情况处理，程序不会自行调回 280W。
