# 本地写作的实际开销与当前加速范围

以下来自本机保留的真实 Ollama 响应指标，只输出数量，不包含课程正文。
这些是指定任务的累计服务指标，包含保留的旧角色和失败响应；不是连续墙钟测速，
也不能按视频文件 GB 数直接推算全部 340 节课程的完成日期。

| 样本 | 响应回执 | 提示 token | 输出 token | 累计模型服务时间 |
| --- | ---: | ---: | ---: | ---: |
| 首份恢复完整稿，14 单元及整篇阅读 | 41 | 956,690 | 143,091 | 3,625.48 秒 |
| 原完整稿覆盖任务，04:31 保留状态 | 99 | 3,773,745 | 75,397 | 4,720.30 秒 |

首份稿的解码时间为 2,768.88 秒，约 51.68 输出 token/秒；提示评估 572.32 秒、
模型加载 276.81 秒。这里大部分服务时间花在较长正文、复核和必要修订的生成上。
完整覆盖样本的提示评估 2,425.32 秒、模型加载 688.55 秒、解码 1,583.74 秒；
多次完整长上下文与模型切换也形成了实际开销。
任务间还有共享 GPU 排队和 CPU 重建、结构验证，不能把上述服务时间当作交付时间。

当前落地的改进见 [下一批写作](course-ready-batch.md)：

- 保存并复用识别、OCR、已完成账本和真实接受回执，后续写作不从视频重做识别。
- 修复作者首次读取不可变账本时的零秒锁冲突，保留原失败和未用角色；不重做 24 组账本。
- 新课程首次生成就约束实际段落数量和合法索引，减少可以事先避免的格式返工。
- 接下来三门完整课优先写较短的一门，缩短下一份稿件的等待；总课程和原文工作量不减少。
- 依赖明确的有限后继自动接续，健康任务完成后不用人工再次启动，也不争抢全课程 worker 锁。

这些改动已准备和实际派发，尚没有足够新稿完成样本来声称整体提升了多少倍。
未来可针对尚未绑定、从未调用的新批次验证同模型角色集中执行、减少切换和更有效的全文匹配，
但不能改变当前已冻结任务的顺序、缩小原文或重问已接受的检查来制造速度提升。
提高功耗受 200W/70°C 硬条件限制，不能替代以上改进。

公开读者成品仍为 1 篇。内部稿、来源笔记、账本或完成覆盖批次都不计为可交付文章；
全文与课件检查、图文和自测质量、整体编辑及实际阅读仍须逐课完成。
